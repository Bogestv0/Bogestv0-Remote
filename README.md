# Bogestv0 REMOTE

Собственная программа удалённого доступа (в духе AnyDesk): свой клиент на Electron + WebRTC и свой
маленький сервер на вашей VPS. Интерфейс сделан по вашему макету.

```
 Устройство A ◄──── экран, звук, ввод: WebRTC, DTLS-SRTP (напрямую или через TURN) ────► Устройство B
      │                                                                                       │
      └──────────── wss (закреплённый сертификат): ID, «кто в сети», служебные offer/ICE ─────┘
                                       │
                          ваша VPS: signaling (Node.js) + coturn
```

* `server/` — сервер сигнализации и TURN (Docker). Видеопотока не видит.
* `client/` — приложение для Windows (трей, автозапуск, захват экрана и звука, ввод, админ-режим).
* `.github/workflows/build-windows.yml` — сборка `.exe` в GitHub Actions.

## 1. Сервер (VPS) — заменяет RustDesk-сервер

```bash
# на VPS: остановить старое (RustDesk), если запущено
cd ~/bogestv0-remote-server && sudo docker compose down

# загрузите папку server/ на VPS (scp/git), затем:
cd server
cp .env.example .env
nano .env                       # PUBLIC_IP уже ваш; TURN_SECRET= вывод команды:  openssl rand -hex 32
chmod +x firewall.sh && ./firewall.sh
sudo docker compose up -d --build
sudo docker compose logs signaling | grep FINGERPRINT     # ← отпечаток сертификата
```

Порты (откройте и в панели хостера, не только в `ufw`): **8443/tcp**, **3478/udp+tcp**, **49160–49200/udp**.
Порты RustDesk 21115–21119 больше не нужны.

## 2. Клиент (.exe)

1. Создайте на GitHub **новый приватный репозиторий** и загрузите в него содержимое этой папки.
2. Вкладка **Actions → Build Windows → Run workflow** (≈ 5–10 минут).
3. В результате запуска, раздел **Artifacts** → `Bogestv0-REMOTE-windows-x64`:
   `…Setup….exe` (установщик, без прав администратора) и `…Portable….exe`.

Адрес сервера `46.226.166.141:8443` уже вшит. При первом подключении приложение запоминает отпечаток
сертификата сервера; чтобы закрепить его строго, вставьте отпечаток из логов сервера в
**Безопасность → Сервер**. После этого подмена сервера невозможна: соединение блокируется.

## 3. Как пользоваться

* На обоих компьютерах запустите программу. У каждого свой ID (9 цифр). **Устройства → Добавить устройство** — вводите ID.
* **Подключение с подтверждением:** на принимающем компьютере появится окно «Разрешить / Отклонить» (авто-отказ через 18 с).
* **Подключение по паролю:** на принимающем — **Безопасность → Задать пароль** и включить «Вход без ручного подтверждения»
  (желательно ограничить «Разрешённые устройства»). Зритель выбирает «По паролю». Баннер о входе показывается всё равно.
* **Админ-доступ:** флажок при подключении или кнопка-щит в панели сессии. На принимающем компьютере — **отдельный** запрос
  и окно Windows UAC, каждый раз, даже при входе по паролю.
* **Вход по паролю сразу с правами администратора:** галочка в окне «Задать пароль» (и переключатель в «Безопасность»). Тогда зашедшие по паролю
  получают админ-доступ без отдельного запроса и без окна UAC. Включение подтверждается один раз системным окном «Да/Нет» на самом компьютере
  и работает только если установлена служба (версия Setup). В портативной версии окно UAC всё равно придётся подтвердить вручную.
  Для входа «с подтверждением» админ-доступ по-прежнему спрашивается отдельно.
* Если у принимающего компьютера несколько мониторов, в панели сессии появится выбор монитора (переключение на лету).
* Буфер обмена (только текст): две кнопки в панели сессии — «отправить мой буфер» и «получить буфер удалённого». Только по нажатию, ничего не синхронизируется само; принимающий компьютер видит уведомление, в журнале остаётся запись.
* Закрытие окна сворачивает в трей; «Выйти полностью» — в меню значка.

## Как устроена защита

* Медиа и ввод шифруются DTLS-SRTP; сервер сигнализации их не получает.
* Пока хозяин устройства (или верный пароль) не разрешил — по каналу не уходит ни кадра.
* Пароль не передаётся: зритель присылает подпись PBKDF2+HMAC, в которую входят одноразовый nonce и **оба отпечатка DTLS**.
  Если сервер сигнализации попытается подменить соединение, подпись не сойдётся.
* 5 неверных паролей с одного ID → блокировка на 10 минут. Пароль на диске хранится зашифрованным (Windows DPAPI).
* Клиент не доверяет «центрам сертификации», а закрепляет сертификат вашего сервера.
* ID привязан к секретному токену устройства — чужой ID занять нельзя.

## Что проверено и что — нет (честно)

Проверено автоматически (`npm test` в `client/` и `server/`, `node test/e2e.js`, `xvfb-run node test/electron-smoke.js`):
протокол сервера; два экземпляра интерфейса соединяются через настоящий WebRTC: видео, звук, микрофон, ввод,
пароль (верный/неверный/блокировка), подтверждение (разрешить/отклонить), отдельный админ-запрос, «занято», список разрешённых,
выбор монитора на лету, буфер обмена в обе стороны (проверено 15 прогонов подряд без сбоев);
настоящий Electron: окно, IPC, TLS, запоминание и сверка отпечатка, отказ при подмене сертификата; упаковка `electron-builder`.

**Не проверено на реальной Windows** (здесь её нет): `SendInput` через koffi (мышь/клавиатура), захват системного звука,
запуск админ-помощника через UAC, автозапуск, трей. Код для них написан по документации WinAPI/Electron, но первый запуск
на Windows — это и есть их проверка. Если что-то не сработает, пришлите описание — поправлю.

## Ограничения версии 0.1

* Нет передачи файлов; буфер обмена — только текст, до 200 тыс. символов.
* Окно UAC и экран блокировки: работают только если приложение поставлено установщиком **Setup** (он ставит службу «Bogestv0 REMOTE», WinSW). Служба сама ничего не принимает из сети: при запросе админ-доступа она показывает системное окно «Да/Нет» в сессии пользователя (его нельзя нажать программно из обычных процессов), и только после «Да» запускает SYSTEM-помощника в вашей сессии. Помощник вводит мышь/клавиатуру на любом рабочем столе и на время UAC/блокировки передаёт кадры вместо обычного захвата. В портативной версии службы нет — остаётся запасной путь через UAC (без UAC-окна и экрана входа).
* Служба, захват защищённого стола и установщик **не проверялись на настоящей Windows** (проверены только логика, размеры структур WinAPI и упаковка). Первый запуск на Windows — возможны правки.
* Админ-помощник слушает `127.0.0.1` с одноразовым токеном и принимает одно соединение; вредоносная программа **того же пользователя**
  теоретически может успеть подключиться раньше. Для этого есть надёжное решение (именованный канал с ACL) — запланировано.
* Сборка не подписана сертификатом: SmartScreen покажет «Неизвестный издатель».
* Принимающая сторона — Windows. Управляющим устройством может быть любой ПК с этим приложением (macOS/Linux-сборки не настроены).
* Лицензия — AGPL-3.0-or-later (рекомендация; поменяйте в `client/package.json`, если нужна другая).

## Обновления программы

* В **Безопасность → Обновления** есть кнопка «Проверить обновления». Приложение также само проверяет новую версию через 30 секунд после запуска и затем раз в 6 часов.
  Когда версия вышла, в верхней панели появляется кнопка **«Обновить до vX.Y.Z»**.
* **Установленная версия (Setup):** по нажатию программа скачивает обновление, устанавливает его и перезапускается. Идущий сеанс завершается (перед этим программа спросит),
  Windows может показать запрос UAC (установка «для всех пользователей»). Скачивание начинается только после вашего нажатия.
* **Портативная версия:** сама заменить себя не может; при выходе новой версии кнопка открывает страницу загрузки.
* Обновления берутся из **GitHub Releases** репозитория `Bogestv0/Bogestv0-Remote` (репозиторий должен быть публичным). Целостность проверяется по хэшу SHA-512 из `latest.yml`.
  Сборка не подписана сертификатом, поэтому защита опирается на доступ к вашему GitHub: кто может публиковать релизы, тот может выпустить обновление.

### Как выпустить новую версию

1. Поднимите `version` в `client/package.json` и `client/package-lock.json` (две строки вверху), запишите изменения в «Журнал изменений».
2. Загрузите изменения в `main` и поставьте тег: `git tag v0.1.7 && git push origin v0.1.7` (тег = версия с буквой `v`).
3. Actions соберут установщик и портативный `.exe` и **сами создадут релиз** с файлами `…Setup….exe`, `…Portable….exe`, `latest.yml` (это важно: без `latest.yml` обновления не находятся).
   Запуск вручную (`Run workflow`) релиз **не** публикует: только собирает файлы в Artifacts.
4. Устройства с версией 0.1.6 и новее увидят обновление сами. **Версии до 0.1.6 обновления не умеют: первый раз поставьте 0.1.6 вручную.**

## Диагностика подключения

* **Клиент:** **Безопасность → Диагностика** — журнал сессии (последние 400 строк) и кнопка «Скопировать». Первая строка показывает версию, ID и режим `relayOnly`.
  Строки `ws …` — события соединения с сервером сигнализации (открытие, `welcome`, закрытие с кодом, приём сообщений, потеря `pong`).
  Код закрытия `4000` означает, что тот же ID подключился с другого экземпляра приложения и сервер закрыл это соединение.
* **Сервер:** `docker logs bogestv0-signaling --since 10m` (из `~/Bogestv0-Remote/server`). В логе: `online`/`offline` с кодом закрытия,
  `signal <offer|answer> от → кому` для каждой пересылки, `НЕ ДОСТАВЛЕНО` (адресат не в сети) и `REPLACED` (второе подключение с тем же ID).
* **Как читать журнал зрителя при неудаче:** должны идти `ws recv signal answer`, затем `sig<- answer`, `answer применён`, `ice connected`.
  Если `answer` не приходит — смотрите лог сервера; если `ws recv` есть, а `sig<-` нет, сообщение потеряно между сокетом и окном.
* `icecandidateerror 701` по `transport=tcp` и поздние `STUN/TURN … timed out` — недоступные виртуальные сетевые интерфейсы (VPN, виртуальные адаптеры); на соединение не влияют.

### Обновление сервера

```bash
cd ~/Bogestv0-Remote && git pull        # если мешают локальные правки server.js: git checkout -- server/server.js
cd server && docker compose up -d --build signaling
docker logs --tail 5 bogestv0-signaling # отпечаток сертификата не должен измениться
```

Каталоги `server/data/` (сертификат, ID) и файл `server/.env` не удалять. Старая папка RustDesk (`hbbs`/`hbbr`) к этому серверу не относится.

  перерисовывал экран сессии и удалял развёрнутый элемент из страницы. Теперь пока окно развёрнуто, подпись, кнопки и статистика обновляются на месте (`client/src/renderer/app.js`).

### 0.1.4
* **Исправлено главное:** зритель не получал `answer` и ICE-кандидаты хоста, соединение завершалось по timeout. Причина — `main.js`: `did-start-loading`

  отдавалась. Теперь очередь включается только при настоящей загрузке окна (`did-start-navigation`, не внутристраничной), плюс страховка на `did-navigate-in-page`.

### 0.1.3
